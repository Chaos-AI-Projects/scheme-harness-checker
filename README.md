# harness-checker

A static analysis tool for Scheme (ChezScheme) programs generated by LLMs. Validates that generated code is safe to execute by checking function whitelists, parameter constraints, and termination properties before running it.

## Features / Analysis Passes

| Pass | Status |
|------|--------|
| Function Whitelist Checking | Implemented |
| Parameter Validation | Implemented |
| Termination Analysis | Implemented |

### Function Whitelist Checking

Ensures every function call in the program uses only approved procedures. Uses a deny-by-default approach — any identifier not explicitly listed in the whitelist is flagged as a violation.

- Whitelist loaded from a plain-text configuration file
- PEG-based tree walker extracts all call-site identifiers
- Handles all scoping forms: `define`, `lambda`, `let`/`let*`/`letrec`/`letrec*`, `case-lambda`, `do`, named `let`, `guard`, `parameterize`
- Forbidden form detection (`syntax-case`, `define-syntax`)
- Quoted forms correctly skipped

### Parameter Validation

Verifies that arguments passed to whitelisted functions satisfy known constraints using a two-pass type inference pipeline:

- **Pass 1 — Constraint Inference** (`pass1-constraints.ss`): Infers parameter type constraints from usage with known operators (e.g., `(+ x 1)` implies x is Number)
- **Pass 2 — Type Inference** (`type-infer.ss`): Forward type checking validates call sites for arity and type mismatches
- Type system (`types.ss`) supports: Number, String, Bool, Char, Symbol, Void, Null, Any, Pair, List, Vector, Function (fixed/variadic), Union, Record, and type variables
- Contradiction detection when a parameter is used as conflicting types
- JSON Schema integration (`json-schema.ss` + `schema-registry.ss`) for loading tool type definitions via `--tool-schemas`
- Standard library type signatures loaded from `data/type-signatures.scm`

### Termination Analysis

Detects programs that may not terminate (infinite loops / unbounded recursion) using a 6-phase analysis pipeline:

1. **Do-loop analysis** — Checks `(do ...)` for non-trivial termination tests, step expressions, and exit-test variable references
2. **Named-let analysis** — Checks for decreasing arguments (`cdr`, `sub1`, `- x 1`) and reachable base cases
3. **Direct recursion** — SCC detection via Tarjan's algorithm, decreasing-argument verification, base case validation
4. **Mutual recursion** — Multi-node SCC analysis requiring all intra-SCC edges to have decreasing args and at least one base case
5. **HOF callback termination** — Checks callbacks passed to known-terminating HOFs (`map`, `for-each`, `filter`, `fold-left`, etc.)
6. **User-defined HOF detection** — Infers which user-defined functions are HOFs and checks their callbacks

Uses a **can-prove model**: functions must be positively proven terminating rather than "not disproven". Configurable definition limit via `--termination-depth N` — programs with more definitions than the limit are blocked with a `definition-limit-exceeded` violation.

## Known Limitations

- **No value-range analysis**: The original Parameter Validation goal (#229) specified "valid value ranges" as a constraint type (e.g., `(vector-ref v idx)` where `idx` must be `0 ≤ idx < (vector-length v)`). The current implementation delivers arity checking and type checking but does not track numeric value ranges or bounds. This is a deliberate scope decision — interval analysis on LLM-generated code adds significant complexity for limited practical benefit given the target use case. This could be revisited as a future enhancement if needed.

## Prerequisites

- [Chez Scheme](https://cisco.github.io/ChezScheme/) (tested with ChezScheme 10.x)
- [packrat-extended](https://github.com/ChaosEternal/packrat-extended) — PEG parser library for s-expression pattern matching. Expected at `../packrat-extended` relative to the project root (or provide the path via `--libdirs`).

## Usage

```sh
scheme --libdirs src:<path-to-packrat-extended> --program src/main.ss [options] <source-file> <whitelist-file>
```

**Options:**

| Flag | Description |
|------|-------------|
| `--no-termination` | Skip the termination analysis phase |
| `--termination-depth N` | Block programs with more than N definitions (emits a definition-limit-exceeded violation; default: no limit) |
| `--tool-schemas <path>` | Load tool type definitions from a JSON Schema file for parameter validation |

**Exit codes:**
- `0` — no violations found (program is safe)
- `1` — violations detected

**Example (clean):**

```
$ scheme --libdirs src --program src/main.ss tests/sample-safe.ss data/minimal-safe.txt
OK: No whitelist violations found.
```

**Example (violations):**

```
$ scheme --libdirs src --program src/main.ss tests/sample-unsafe.ss data/minimal-safe.txt
VIOLATIONS FOUND:
  - system (call in bad-sort body)
  - delete-file (call in cleanup body)
2 violation(s) total.
```

## Whitelist Format

The whitelist is a plain text file with one allowed identifier per line. Lines starting with `;` are comments.

```
; Arithmetic
+
-
*
/

; Boolean
not
boolean?
```

The default whitelist is provided at `data/minimal-safe.txt` and covers safe R6RS/R7RS procedures (arithmetic, list operations, string handling, basic output).

## Scope

- **Target language**: Scheme (ChezScheme dialect)
- **Target input**: LLM-generated programs — expected to be relatively simple and well-structured
- **Out of scope**: Macros (`syntax-case`, `define-syntax`, etc.) are forbidden and flagged as violations
